# npm Publish Flow — @mux-protocol/contracts

This document describes the process for releasing a new version of the
`@mux-protocol/contracts` TypeScript package to npm.

---

## Current state: publishing is manual

**There is no automated publish pipeline today.** `.github/workflows/`
contains only `ci.yml` and `deploy.yml`. The `bindings` job in `ci.yml` runs
`npm ci` → lint → `tsc --noEmit` → `npm test` → `npm run build` on every push
and PR — it does **not** call `stellar contract bindings typescript`, does
not check for binding drift, and does not run `npm publish`. There is no
`NPM_TOKEN` secret configured and no `bindings.yml` workflow file. A prior
version of this document described a fully automated `chore: release` →
CI-publishes flow; that pipeline does not exist in this repository. Until
someone builds it, use the manual process below for every release.

---

## Prerequisites

### npm Access Token (for whoever runs the manual publish)

A local npm login with **publish** rights to the `@mux-protocol` scope:

```bash
npm login
```

### Package Scope

The package is published as `@mux-protocol/contracts` (scoped, public).
Scoped packages are private by default on npm — always pass
`--access public`.

## Step-by-Step Manual Release Process

### 1. Regenerate and check bindings for drift

```bash
bash scripts/build-wasm.sh --release
bash scripts/generate-bindings.sh
git status bindings/src/generated/
```

If `generate-bindings.sh` changes anything under `bindings/src/generated/`,
that means the committed bindings were stale relative to the current
contract WASM — commit the regenerated files before continuing.

Note: `scripts/generate-bindings.sh`'s `CONTRACTS` list must be kept in
sync with `contracts/`. If a contract exists under `contracts/` but is
missing from that script's list, its bindings will not be regenerated by
this step — check the script if a contract seems out of date.

### 2. Bump the version

`bindings/package.json`'s `version` must equal the root Cargo workspace
`[workspace.package].version` — this is enforced by
`bindings/__tests__/version-sync.test.ts` (run via `npm test`, calling
`scripts/sync-versions.sh --check`). Bump both together, following
[semver](https://semver.org/) — see
[`docs/BREAKING_CHANGES.md`](BREAKING_CHANGES.md) for what counts as a
MAJOR change, including the error-enum-specific rules there.

```bash
# Update the workspace version in the root Cargo.toml, then:
bash scripts/sync-versions.sh
```

### 3. Verify locally

```bash
cd bindings
npm ci
npm run lint
npx tsc --noEmit
npm test
npm run build
```

All of these must pass — they mirror the `bindings` CI job, which will also
run on the release commit's PR/push but does not gate or perform the
publish itself.

### 4. Commit and merge

```bash
git add Cargo.toml bindings/package.json bindings/src/generated/
git commit -m "chore: release v<new-version>"
git push origin main
```

There is no commit-message-triggered automation today; the `chore: release`
prefix is a convention for readability in `git log`, not a CI gate.

### 5. Publish

```bash
cd bindings
npm publish --access public
# You will be prompted for an OTP if 2FA is enabled on your npm account.
```

### 6. Verify the release

```bash
npm view @mux-protocol/contracts version
npm install @mux-protocol/contracts@<new-version>
```

### 7. Tag the release

```bash
git tag v<new-version>
git push origin v<new-version>
```

`scripts/check-changelog-release-artifacts.sh` (run in CI) checks that
tagged releases have WASM hashes and a matching binding version recorded in
`CHANGELOG.md` — update `CHANGELOG.md` before or alongside tagging.

## npm Provenance Attestation

Manual `npm publish` from a local machine does **not** produce a
[SLSA provenance attestation](https://slsa.dev/) — that requires publishing
from within GitHub Actions with OIDC (`npm publish --provenance`), which is
only possible once an automated publish workflow exists (see below). Until
then, published versions carry no provenance attestation.

---

## Path to automation (not yet implemented)

If a `bindings.yml` GitHub Actions workflow is built in the future, it
should include, at minimum: a `generate-bindings` job (regenerate from the
built WASM), a `check-binding-drift` job (fail a PR if generated bindings
differ from committed state), and a gated `publish` job using an `NPM_TOKEN`
secret and `npm publish --provenance --access public`. This document should
be rewritten to describe that flow as primary once it exists in
`.github/workflows/` — do not restore the "fully automated" framing until
the workflow file is actually present in this repository.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `403 Forbidden` from npm | Not logged in, or account lacks publish rights to `@mux-protocol` | `npm login`; confirm scope access on npmjs.com |
| `402 Payment Required` | Package is private (scoped default) | Pass `--access public` |
| `version-sync.test.ts` fails | `bindings/package.json` version doesn't match Cargo workspace version | Run `bash scripts/sync-versions.sh` |
| Bindings differ from WASM after `generate-bindings.sh` | Contract changed since bindings were last regenerated | Commit the regenerated files under `bindings/src/generated/` |
| `tsc --noEmit` fails | Type errors in generated or hand-authored TS | Fix type errors before publishing |
| OTP prompt during `npm publish` | 2FA enabled on your npm account | Enter the OTP from your authenticator |
